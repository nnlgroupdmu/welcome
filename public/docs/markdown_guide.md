### 🧭 引言：为什么在 PPT 之外，我们还需要 Markdown？

在我们的日常科研中，用 PPT 记录和汇报项目进展已经是一种习惯，在每次开组会都要用到，能让导师和同门在几分钟内直观地看到你的进展。

但随着我们把项目的各种细节塞进 PPT，大家在实际操作中可能也会发现，PPT 并不是一个优秀的项目管理工具。

科研是一个高频迭代、充满碎片的动态过程。如果你试图把每一次的代码微调、环境配置的拼写错误、或者跑了三天刚出来的中间态数据，都塞进 PPT 的文本框里，不仅排版极其痛苦，页码爆炸后会越来越卡顿，想找某个技术细节时，更无异于大海捞针。

更合理的工作流应该是：用 PPT 来“对外展示结果”，用 Markdown 笔记来“对内管理项目”。

项目管理的本质是记录细节：你今天调小了一个超参数、AI 帮你重构了一个函数、或者遇到一个奇怪的 CUDA 报错，这些高频、细碎的技术细节，直接用纯文本的 Markdown 顺手丢进本地笔记里。它不消耗你的排版精力，却能帮你完整拉出一条清晰的实验生命周期。

组会汇报时厚积薄发：到了需要做 PPT 汇报时，你不再需要面对空白的幻灯片痛苦回忆。直接打开本地的 Markdown 文件夹，里面的实验对照组、代码块和 AI 总结都是现成的，直接复制粘贴，几分钟就能拼出一份逻辑严密、数据硬核的汇报 PPT。

Markdown 不仅是简单的排版语法，更是 **AI 时代最完美的纯文本数据资产**。我们已经在内网推行了基于 Markdown 的 Memos 广场，那么在本地端，如何高效、规范地记录笔记，就成了提升科研效率的关键。以下是为你整理的一套符合计算机专业习惯的笔记规范与工作流建议。

## 一、 工具推荐：为什么是 Obsidian？

在众多 Markdown 编辑器中，实验室强烈推荐 **Obsidian（黑曜石）** 作为你的主力笔记软件。

* **纯文本与本地优先**：你的所有笔记都是真实的 `.md` 文件，不会有笔记平台之间格式不兼容的问题。保存在你自己的硬盘上，这意味着**数据绝对安全**，不会因为某家云笔记厂商倒闭或收费而丢失。
* **双向链接（Backlinks）**：你可以通过 `[[笔记名称]]` 将两篇看似不相关的 Bug 记录或论文联系起来，久而久之，你的笔记会像大脑神经元一样，自动织成一张**网状的知识图谱**。
* **程序员友好**：它的文件组织形式与存储路径相同，非常清晰直观。它对代码高亮、LaTeX 数学公式、Mermaid 流程图的原生支持极佳。配合丰富的社区插件（如 Git 自动同步），完全是为计算机专业量身定做的 IDE。

> 💡 **平替参考**：如果你追求极致的轻量与秒开，**Typora**（最新版收费）或 **VS Code**（配合 Markdown All in One 插件）也是非常优秀的纯文本选择。

## 二、 本地知识库对每个人的实际意义
如果把记笔记当成一种“文学创作”或“写日记”，确实非常消耗精力，也很难长期坚持。特别是对于计算机专业的同学，大家更习惯直接在终端和代码中解决问题。

因此，我们推荐构建本地知识库，并不是为了追求形式上的工整，而是基于以下三点效率考量：

### 1. 它是对抗记忆力衰退的“备忘录”
计算机专业的配置命令、环境依赖和特定框架的报错极其繁杂。很多时候，你花了两天时间解决了一个显卡驱动与 PyTorch 版本的兼容性问题；两三个月后，当你重新配置新环境或同门遇到类似问题时，你大概率已经忘记了当初的解决命令。
本地知识库的作用是充当你的“内存转储（Dump）”。遇到复杂的报错或好用的单行脚本，随手复制到本地，不需要排版。下次再遇到时，在本地一秒检索，即可直接复用，避免把时间浪费在重复 Google 和查阅 history 记录上。

### 2. 它是为你定制的“AI 上下文”
目前大家都在频繁使用 ChatGPT 或 Claude。但公版大模型没有你的项目背景，你每次提问，都不得不重复解释你的系统环境、数据集格式和代码架构。
Markdown 是最纯粹的纯文本，也是对大语言模型（LLM）最友好的数据格式。当你本地积累了数十篇粗糙、无排版的开发日志、代码片段和 AI 的改动列表后，你可以让大模型直接挂载你的笔记文件夹。
届时，你不再需要自己去翻笔记，只需对本地 AI 提问：“帮我看看我 4 月份跑那个多模态模型时，最后把学习率调到多少才收敛的？” 或者是 “根据我之前的记录，这个报错可能是什么原因？” AI 就会直接基于你过去的数据给出精准回答。你不习惯整理没关系，AI 擅长。但前提是，你得先在本地硬盘里为它准备好这些机读的纯文本数据。

### 3. “纯文本优先”的数据所有权
将技术知识和个人代码片段托付给市面上的商业云笔记（如 Notion、语雀等），不仅面临格式不兼容的迁移成本，还要承担平台收费或数据泄露的风险。
Obsidian 管理的本地 .md 文件在底层就是普通的纯文本。这意味着你的资产完全由自己控制，即便软件不联网、甚至未来被彻底淘汰，你的所有记录依然可以用最简陋的终端文本编辑器（如 Vim）秒级打开，具有最高的兼容性和生命周期。

## 三、 规范与排版建议

写 Markdown 的核心克制在于：**依靠结构，而非视觉。** 因此对 AI 非常友好。使用时建议遵循的规范：

* **从二级标题（`##`）开始**：
一篇笔记的文件名通常已经是自然的一级标题（`#`）。在正文内部，请从 `## 二级标题` 开始建立目录架构。这样在导出或在其他平台渲染时，能保持最严谨的树状层级。
* **极简原则：尽量不要插入本地图片**：图片存储占用高，在 Markdown 中要用链接的形式管理。
* *建议*：能用**文字、代码块、或文本表格**表达的，绝不用截图；
* *进阶*：如果必须画流程图或架构图，优先学习使用 **Mermaid 语法**（直接用文本写出代码，Obsidian 会自动渲染成漂亮的流程图）。


* **保持纯文本的“机读性”**：
不要使用花哨的字体颜色或过于复杂的 HTML 标签。最干净的、由 `##` 标题、`*` 列表、`- [ ]` 任务框构成的纯文本，才是大语言模型（LLM）最喜欢、最容易理解的黄金数据。

## 四、 高效的日常笔记习惯（从何处开始下手？）

很多同学面对空白的笔记软件不知道写什么，你可以尝试将 Markdown 深度融入你每天的“实验/开发生命周期”中：

### 1. 每日记录（Daily Notes）—— 科研日志

在 Obsidian 中开启 Daily Notes 插件。每天都可以生成一页当天的笔记。

* **今天计划做什么**：用 `- [ ]` 列出实验、调参和文献任务。
* **今天遇到了什么**：今天改了哪些代码，跑实验时报了什么错，随手贴在里面。即使今天没有解决，它也是最真实的科研轨迹。

### 2. 每次修改与代码提交的总结（Commit & Retrospect）

当你对实验代码做了一次重大重构、或者微调了模型架构时，除了在 Git 里写一句模糊的 Commit，更要在本地笔记里留下深度的**实验对照组记录**：

> 比如：“5月27日修改：将学习率从 `1e-4` 降至 `5e-5`，引入了第 4 层的残差连接。原因：观察到 Epoch 20 后 Loss 发生轻微震荡。”

### 3. 摘录与沉淀 AI 的改动列表

现在大家都在大量使用 ChatGPT / Claude 辅助写代码。**不要让 AI 帮你写完代码后，点击复制就完事了。**

* **习惯**：把 AI 帮你重构代码时的“改动说明（Changelog）”以及它指出的潜在 Bug 隐患，摘录进你的本地笔记。
* **价值**：这是性价比最高的学习过程。这些被 AI 梳理过的干净文本，会成为你日后写论文、写致谢或者解决类似 Bug 时最快被检索到的无价财富。

---

## 五、 最终的目的：让“知识”流动起来

当你在本地用 Obsidian 积累了大量的硬核 Markdown 笔记后，不要让它们在你的硬盘里“发霉”。

1. **碎片化提炼**：当你从这堆本地笔记里，提炼出了一个全组通用的环境配置方案、或者一个踩坑解法，请果断把它发布到实验室的 **Memos 广场** 上（带上 `#GPU踩坑` 或 `#常用脚本` 等标签）。
2. **构建共同体**：你在本地踩过的一个小坑，发布出来可能就能拯救隔壁工位今晚调参到深夜的师弟。

安装好 Obsidian，让我们一起把日常的劳动，转化为实验室可以长久传承的代码与知识资产。
